# Firebase Hosting Deployment — PdskWork (Spark / free plan)

PdskWork deploys to **Firebase Hosting on the free Spark plan** as a fully
**static export**. No App Hosting, Cloud Functions, or Cloud Run are used
(those require the Blaze pay-as-you-go plan). All dynamic behavior — the admin
CMS, blog CRUD, and locale — runs **client-side** using **Firestore** and
**Firebase Authentication** (both available on the free tier).

## Architecture

| Concern | Approach |
|---|---|
| Rendering | `output: 'export'` → static HTML in `out/`, served by Hosting CDN |
| Blog data | Firestore `posts` collection (client SDK reads/writes) |
| Admin auth | Firebase Auth (email/password) — no httpOnly cookie (no server) |
| Route protection | Client-side `AdminGate` redirects unauthenticated visitors |
| Public blog | Client components fetch Firestore on mount; seed slugs pre-rendered for SEO |
| Dynamic blog slugs | Firebase Hosting rewrite `/blog/{slug}` → `/blog/_` placeholder (client reads slug from `window.location`) |
| Admin edit route | Rewrite `/admin/blog/{id}/edit` → `/admin/blog/_/edit` (client reads id from path) |
| Sitemap / robots | Generated at build from seed `src/db/blog.json` (`force-static`) |
| RSS feed | Static `public/feed.xml` generated by `npm run prebuild` (`scripts/gen-feed.mjs`) |

### Build-time vs runtime data

Static export has no server runtime, so there are two blog data paths:

- **Build-time** (`src/lib/blog-seed.ts`) reads the committed `src/db/blog.json`
  synchronously. Used by `generateStaticParams`, `generateMetadata`, `sitemap.ts`,
  and the RSS feed so seed posts get static HTML + SEO metadata.
- **Runtime** (`src/lib/blog-firestore.ts`) reads/writes Firestore from the
  browser. Used by public blog pages and the admin CMS for live data.

Seed posts should be imported into Firestore once (see step 4) so the two stay
in sync. Posts created via the admin CMS afterward live only in Firestore and
appear on the public blog immediately (client-rendered); they appear in the
sitemap/feed after the next build+deploy.

## Files

| File | Purpose |
|---|---|
| `next.config.ts` | `output: 'export'`, `images.unoptimized`, `distDir: 'out'` |
| `firebase.json` | Hosting config (`public: out`), rewrites, cache headers |
| `.firebaserc` | Default project alias (`pdskwork`) |
| `firestore.rules` | Public read of published posts; auth-required writes |
| `firestore.indexes.json` | Composite indexes for the blog queries |
| `src/lib/firebase.ts` | Client SDK init (app, auth, db, analytics) |
| `src/lib/blog-firestore.ts` | Runtime blog store (Firestore client) |
| `src/lib/blog-seed.ts` | Build-time seed reader (fs) |
| `src/lib/use-admin-auth.ts` | Firebase Auth hook for the admin UI |
| `src/components/AdminGate.tsx` | Client-side auth guard |
| `scripts/gen-feed.mjs` | Pre-build RSS generator |
| `scripts/seed-firestore.mjs` | One-time Firestore seed importer |

## 1. Prerequisites

- Google account + Firebase project **pdskwork** (Spark/free plan is fine).
- Firebase CLI: `npm install -g firebase-tools` then `firebase login`.
- `firebase use pdskwork` (already configured in `.firebaserc`).

## 2. Enable Firestore + Auth

In the Firebase console for **pdskwork**:

- **Firestore Database** → Create database (production mode). Then deploy the
  rules + indexes:
  ```bash
  firebase deploy --only firestore:rules,firestore:indexes
  ```
- **Authentication** → Sign-in method → enable **Email/Password**.

## 3. Create the admin user

- **Authentication → Users → Add user**: set the admin email + password you'll
  use to sign in at `/admin/login`.
- (Optional) Lock writes to that single user by editing `firestore.rules`:
  set `ADMIN_UID` in the `isAdmin()` helper to the user's uid, then redeploy
  the rules.

## 4. Seed Firestore from blog.json (one time)

Generate a **service account key** (Admin SDK credentials — this is a secret,
keep it out of git): Firebase console → **Project settings → Service accounts →
Generate new private key** → save as `serviceAccountKey.json` in the repo root
(already gitignored). Then:

```bash
npm run seed:firestore
```

This imports the two committed seed posts into the `posts` collection using the
Firebase Admin SDK (which bypasses security rules, so it works in production
mode). Delete `serviceAccountKey.json` when done, or keep it locally only.

## 5. Build + deploy

```bash
npm run build        # runs prebuild (feed.xml) then `next build` → out/
firebase deploy --only hosting
```

`firebase.json` points Hosting at `out/`. The custom domain **pdsk.qd.je** is
configured in the console: **Hosting → Add custom domain → pdsk.qd.je**, then
add the DNS records Firebase shows you at your registrar.

## 6. CI/CD — GitHub Actions (automatic deploy)

A push to `master` (or a manual run) triggers `.github/workflows/firebase-deploy.yml`,
which runs `npm run build` and deploys `out/` to Firebase Hosting via the
`FirebaseExtended/action-hosting-deploy` action.

### Setup the deploy key (one time)

1. Firebase console → **Project settings → Service accounts → Generate new
   private key** → download the JSON.
2. GitHub repo → **Settings → Secrets and variables → Actions → New repository
   secret** → name it `FIREBASE_SERVICE_ACCOUNT` → paste the full JSON value.
3. Done. The next push to `master` deploys automatically.

The workflow uses Node 22, caches npm, sets the public `NEXT_PUBLIC_*` env vars
for the build, and verifies `out/index.html` exists before deploying.

## 7. Custom domain — pdsk.qd.je

The auto-deploy is already live at the default URL `https://pdskwork.web.app`.
To serve the same content on your custom domain **pdsk.qd.je**, connect it once
in the Firebase console (this step needs your DNS registrar access, so it can't
be done by CI):

1. Firebase console → **pdskwork** project → **Hosting** → **Add custom domain**.
2. Enter `pdsk.qd.je` → **Continue**. (Skip "Quick setup" for the apex/root domain.)
3. Firebase shows you **A records** and a **TXT verification record**. Example
   values Firebase typically gives (use the exact ones the console shows you):

   | Type | Host/Name | Value |
   |---|---|---|
   | TXT | `pdsk.qd.je` (or `@`) | `firebase-site-verification=…` |
   | A   | `pdsk.qd.je` (or `@`) | `151.101.1.195` |
   | A   | `pdsk.qd.je` (or `@`) | `151.101.65.195` |
   | A   | `pdsk.qd.je` (or `@`) | `151.101.129.195` |
   | A   | `pdsk.qd.je` (or `@`) | `151.101.193.195` |

4. At your **DNS registrar** for `qd.je` (the dashboard where you manage the
   `qd.je` zone), add the records from step 3. The Host/Name field is usually
   `pdsk` (the subdomain) or `@` for the apex — your registrar's UI tells you.
5. Back in the Firebase console, click **Verify** / **Finish**. Firebase polls
   DNS; once the TXT verifies, it provisions a **managed SSL certificate**
   automatically (no manual cert needed). This can take ~15 min – a few hours.
6. When status shows **Connected** with a green check, visit
   **https://pdsk.qd.je** — it serves the latest `master` deploy.

You can verify DNS propagation from a terminal:

```bash
# A records should resolve to Firebase's IPs:
dig +short pdsk.qd.je A
# Or via Google's DoH:
curl -s "https://dns.google/resolve?name=pdsk.qd.je&type=A"
```

Notes:
- `qd.je` is a `.je` (Jersey) TLD — make sure your registrar supports editing
  the A/TXT records for the `pdsk` subdomain. If `qd.je` itself is the apex,
  use `@` as the name.
- The custom domain points at the **same Hosting site** (`pdskwork`) that CI
  deploys to, so every `master` push updates `pdsk.qd.je` automatically — no
  extra config in the workflow.
- Both `pdskwork.web.app` and `pdsk.qd.je` stay active; you can keep the
  `.web.app` URL as a fallback.

## Notes

- Analytics (Google Analytics for Firebase) initializes client-side via
  `<FirebaseAnalytics />` in the root layout; measurementId `G-XH5XF12NSD`.
- `next/image` is set to `unoptimized` (no server optimizer). Use plain
  `<img>` or pre-optimized images.
- The admin pages are `noindex` (see `admin/layout.tsx`).
- Locales: still cookie + context based (`LocaleProvider`), fully client-side.
